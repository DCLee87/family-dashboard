# E4 일정 상세 유스케이스

- 상태: 초안
- 작성일: 2026-07-29
- 기준: FR-SCH-001~036, FR-LOC-001~014, ADR-002~009, ADR-027

## 공통 액터와 조건

### 액터

- `관리자`: 등록된 PC, 부모 모바일 또는 공용 태블릿에서 관리자 모드를
  잠금 해제한 사용자
- `보기 사용자`: 등록된 부모·딸 개인 기기 또는 등록된 공용 기기
- `예약 작업`: 휴지통 보존 기한과 후속 자동 처리를 수행하는 서버 작업

### 공통 사전 조건

- 가족 시스템의 최초 설정이 완료되어 있다.
- 요청 기기는 등록되어 있고 폐기되지 않았다.
- 시스템 시간대는 `Asia/Seoul`로 설정되어 있다.
- 쓰기 유스케이스는 유효한 관리자 모드를 요구한다.

### 공통 사후 조건

- 성공한 쓰기는 사용 기기와 UTC 시각을 감사 기록에 남긴다.
- 실패한 쓰기는 일정, 대상 가족, 요일과 예외 중 일부만 저장하지 않는다.
- 보기 응답은 서버가 기기 프로필과 권한을 판정한 뒤 생성한다.

## UC-010 일정 등록

### 목표

관리자가 일회성 또는 매주 반복 일정을 한 명 이상의 가족에게 등록한다.

### 정상 흐름

1. 관리자가 일정 등록 화면을 연다.
2. 시스템은 활성 가족 구성원과 기본 공개 범위 `가족 공개`를 제공한다.
3. 관리자는 제목, 대상 가족 한 명 이상과 공개 범위를 입력한다.
4. 관리자는 시간 일정 또는 종일 일정을 선택한다.
5. 시간 일정이면 시작·종료 시각을, 종일 일정이면 포함 시작일·종료일을
   입력한다.
6. 선택적으로 장소, 메모와 종일 일정의 상태 반영 시간 구간을 입력한다.
7. 선택적으로 매주 반복, 요일 한 개 이상, 시작일과 종료일을 입력한다.
8. 시스템은 형식, 날짜·시간 순서와 허용된 필드 조합을 검증한다.
9. 시스템은 최종 회차를 펼쳐 대상 가족의 기존 일정과 겹침을 검사한다.
10. 겹침이 없으면 일정, 대상 가족과 반복 요일을 한 트랜잭션으로 저장한다.
11. 시스템은 생성된 일정 ID와 현재 버전, 공개 범위를 반환한다.

### 대안·오류 흐름

- 대상 가족이 없으면 `schedule_participants_required`로 저장을 거부한다.
- 종료가 시작과 같거나 빠르면 `invalid_time_range`로 거부한다.
- 종일 종료일이 시작일보다 빠르면 `invalid_date_range`로 거부한다.
- 반복 요일이 없으면 `weekly_days_required`로 거부한다.
- 지원하지 않는 반복 규칙이면 `unsupported_recurrence`로 거부한다.
- 요청된 회차 조회 범위가 62일을 넘으면
  `schedule_range_too_large`로 거부한다.
- 겹치는 일정이 있으면 저장하지 않고 `overlap_warning`, 겹친 회차의
  안전한 요약과 일회용 확인 토큰을 반환한다.
- 관리자가 같은 입력과 확인 토큰으로 다시 요청하면 겹침을 허용하고
  저장한다.
- 확인 토큰의 입력 내용이 달라졌거나 만료됐으면 새 겹침 검사를 요구한다.
- 관리자 모드가 만료됐으면 `admin_session_required`로 거부한다.

### 인수 기준

- 맞닿기만 한 `[09:00,10:00)`과 `[10:00,11:00)`은 겹치지 않는다.
- 여러 대상 중 한 명에게만 겹쳐도 그 가족을 포함한 경고가 발생한다.
- 부모 전용으로 겹친 일정은 권한 없는 확인 화면에 상세가 노출되지 않는다.
- 저장 성공 후 지정된 모든 가족의 일정 조회에 회차가 나타난다.

## UC-011 일정 수정과 반복 회차 예외

### 목표

관리자가 일정 전체를 수정하거나 반복 일정의 한 회차만 변경·취소한다.

### 전체 일정 수정 흐름

1. 관리자가 일정 상세를 연다.
2. 시스템은 현재 버전과 수정 가능한 원본 값을 제공한다.
3. 관리자가 필드를 변경해 현재 버전과 함께 저장한다.
4. 시스템은 UC-010과 같은 검증·겹침 확인을 수행한다.
5. 기존 회차 예외가 새 규칙에서 더 이상 유효하지 않으면
   `occurrence_exception_conflict`와 충돌 목록을 반환한다.
6. 충돌이 없으면 원본을 갱신하고 새 버전을 반환한다.

### 한 회차 변경 흐름

1. 관리자가 최종 회차 상세에서 `이번 회차만 변경`을 선택한다.
2. 시스템은 원래 `occurrence_key`와 변경 가능한 제목, 장소, 메모,
   시간·날짜를 제공한다.
3. 관리자가 값을 변경한다.
4. 시스템은 시간과 겹침을 검증한다.
5. 시스템은 원래 회차 키에 `overridden` 예외를 저장한다.
6. 조회 시 해당 회차만 변경된 값으로 표시되고 다른 회차는 유지된다.

### 한 회차 취소 흐름

1. 관리자가 `이번 회차만 취소`를 선택하고 확인한다.
2. 시스템은 원래 회차 키에 `cancelled` 예외를 저장한다.
3. 해당 회차는 일반 조회, 겹침과 예상 상태 계산에서 제외된다.

### 대안·오류 흐름

- 클라이언트 버전이 오래됐으면 `409 schedule_version_conflict`를 반환하며
  서버 값을 덮어쓰지 않는다.
- 회차 키가 원본 규칙에 존재하지 않으면 `occurrence_not_found`로 거부한다.
- 같은 회차의 예외가 이미 바뀌었으면 `409 occurrence_version_conflict`를
  반환한다.
- 이동된 회차도 화면 날짜가 아닌 원래 회차 키로 다시 수정·취소한다.
- 전체 반복 수정과 한 회차 수정의 차이를 저장 전에 명확히 표시한다.

### 인수 기준

- 화요일 회차를 수요일로 옮겨도 목요일 회차는 바뀌지 않는다.
- 옮긴 회차는 원래 화요일 회차 키로 다시 찾을 수 있다.
- 취소한 회차는 재시작 후에도 다시 생성되지 않는다.
- 원본 수정 중 예외를 묵시적으로 삭제하거나 다른 날짜로 이동하지 않는다.

## UC-012 가족별 일정 조회

### 목표

보기 사용자가 허용된 최종 일정 회차를 가족과 날짜 범위로 조회한다.

### 정상 흐름

1. 사용자가 일정 화면을 연다.
2. 클라이언트는 포함 날짜 범위와 선택적 가족 구성원 ID를 요청한다.
3. 시스템은 일회성 일정과 반복 규칙을 요청 범위에서만 펼친다.
4. 시스템은 취소·변경 예외와 휴지통 상태를 적용한다.
5. 시스템은 인증된 기기 프로필에 맞게 공개 범위를 투영한다.
6. 시스템은 시스템 시간대, 최종 회차와 겹침 표시를 반환한다.
7. 화면은 종일 일정과 시간 일정을 구분해 각 적용 날짜에 표시한다.

### 대안·오류 흐름

- 날짜 범위가 없거나 62일을 넘으면 검증 오류를 반환한다.
- 존재하지 않거나 비활성인 가족 필터는 `family_member_not_found`로
  거부한다.
- 폐기된 기기는 가족 데이터 없이 인증 오류를 받는다.
- 반복 생성 중 하나의 잘못된 규칙이 발견되면 부분 응답 대신 서버 오류와
  진단 ID를 반환하되 민감한 일정 내용을 로그에 남기지 않는다.

### 인수 기준

- 여러 날 종일 일정은 시작일과 종료일을 포함한 모든 날짜에 표시된다.
- 취소 회차는 없고 변경 회차는 최종 값 하나만 나타난다.
- 하나의 일정에 지정된 모든 가족의 필터 결과에 같은 회차가 나타난다.
- 부모 전용 상세는 권한 없는 응답 객체에 포함되지 않는다.

## UC-014 공개 범위에 맞는 조회

### 목표

사용자와 공용 기기가 허용된 정보만 받고 민감한 세부사항을 추론하지
못한다.

### 권한 흐름

1. 시스템은 저장된 기기 인증정보로 소유자와 기기 프로필을 판정한다.
2. 부모 개인 기기에는 세 공개 범위의 상세를 반환한다.
3. 딸 개인 보기에는 `가족 공개`와 `TV 요약` 상세를 반환한다.
4. 공용 태블릿과 TV에는 `가족 공개` 상세와 `TV 요약`의 안전한 요약만
   반환한다.
5. `부모 전용`은 권한 없는 일정 목록에서 제외한다.
6. 부모 전용 일정이 예상 상태를 결정할 때만 별도 비식별 상태 DTO로
   `개인 일정`과 종료 시각을 반환한다.

### 공격·오류 흐름

- 요청 본문의 기기 유형, 소유자와 역할 값은 권한 판정에 사용하지 않는다.
- 권한 없는 상세 ID를 직접 조회하면 존재 여부를 구별하기 어렵게
  `404 Not Found`를 반환한다.
- 요약 DTO에는 원본 ID, 제목, 장소, 메모, 날씨 지역과 상세 URL을
  포함하지 않는다.

### 인수 기준

- 각 권한 조합을 직렬화한 응답 전체에서 금지 필드와 원문을 검색해
  발견되지 않아야 한다.
- 같은 인증정보로 프로필 쿼리를 바꿔도 응답 권한이 상승하지 않는다.
- 모바일 Push와 이후 실시간 갱신도 동일한 투영 서비스를 사용한다.

## UC-015 일정 겹침 확인

### 목표

관리자와 보기 사용자가 겹친 일정을 인지하면서 실제 생활의 중복 일정을
저장·조회한다.

### 흐름

1. 저장 시 시스템은 대상 가족별 최종 시간 구간을 비교한다.
2. 교차하는 구간이 있으면 해당 가족과 회차를 경고한다.
3. 관리자가 확인하면 중복을 허용해 저장한다.
4. 일정 목록과 상세는 겹친 회차를 표시한다.
5. 예상 상태는 ADR-027의 결정 순서로 하나를 선택하되 `일정 겹침`을
   함께 반환한다.

### 인수 기준

- 종일 일정은 명시적 상태 반영 시간 구간이 있을 때만 시간 겹침과 상태
  후보가 된다.
- 시작 시각이 같은 후보는 서버 재시작과 조회 순서에 무관하게 같은
  결과를 선택한다.
- 겹침 경고는 저장 금지가 아니며 명시적인 확인 없이 우회할 수 없다.

## UC-013 일정 삭제와 복원

### 목표

관리자가 한 회차 또는 전체 일정을 삭제하고 보존 기간 안에 복원한다.

### 전체 삭제·복원 흐름

1. 관리자가 `전체 반복` 또는 일회성 일정 삭제를 선택한다.
2. 시스템은 영향 범위를 보여주고 확인을 요구한다.
3. 확인 후 `deleted_at`을 기록해 휴지통으로 이동한다.
4. 일반 조회, 겹침과 예상 상태에서 즉시 제외한다.
5. 삭제 후 30일 안에는 관리자가 휴지통에서 복원할 수 있다.
6. 복원 시 겹침을 다시 검사해 경고하지만 복원 자체를 막지 않는다.

### 영구 삭제 흐름

1. 관리자가 휴지통에서 영구 삭제를 선택하고 재확인한다.
2. 시스템은 원본, 참여자, 요일과 예외를 한 트랜잭션으로 삭제한다.
3. 예약 작업은 보존 기한이 지난 항목을 같은 방식으로 삭제한다.

### 인수 기준

- 반복의 `이번 회차만 삭제`는 UC-011의 취소 예외를 만들고 원본을
  휴지통으로 이동하지 않는다.
- 30일 경계는 삭제 UTC 시각을 기준으로 계산한다.
- 영구 삭제 실패 시 하위 데이터 일부만 없어지지 않는다.
- 휴지통과 영구 삭제 API는 관리자 모드 없이는 사용할 수 없다.

## UC-020 일정 기반 가족 예상 상태

### 목표

보기 사용자가 GPS가 아닌 허용된 일정으로 계산한 가족별 예상 상태를
확인한다.

### 정상 흐름

1. 클라이언트가 기준 시각을 보내거나 서버 현재 시각을 사용한다.
2. 시스템은 가족별 활성 장소 일정 회차를 찾는다.
3. 시작 시각이 가장 늦은 회차를 선택하고 ADR-027 동률 규칙을 적용한다.
4. 공개 범위 투영 후 상태, `일정 기준`, 적용 종료 시각과 겹침 여부를
   반환한다.
5. 활성 장소 일정이 없으면 기본 상태 또는 `일정 없음`을 반환한다.

### 인수 기준

- 종일 일정은 상태 반영 구간이 있을 때만 후보가 된다.
- 부모 전용 후보가 선택되면 권한 없는 기기에는 `개인 일정`과 종료
  시각만 반환한다.
- 응답은 실제 위치라고 표현하지 않고 항상 `일정 기준` 출처를 표시한다.
- 현재 시각이 일정 종료와 같으면 그 일정은 활성 상태가 아니다.

## 공통 비기능 인수 기준

- 회차 계산, 겹침과 공개 범위 투영은 단위 시험 가능한 순수 도메인
  함수로 구현한다.
- 쓰기 트랜잭션과 권한 행렬은 SQLite·HTTP 통합 시험으로 검증한다.
